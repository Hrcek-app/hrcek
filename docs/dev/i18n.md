# Internationalisation

Every user-facing string is translatable. Hrček ships English (the
source language) and Slovenian.

## Writing translatable strings

At module level, where the string is evaluated at import time:

```python
from django.utils.translation import gettext_lazy as _

MESSAGE = _("The saved item does not exist.")
```

Inside a function, where the active language is already known:

```python
from django.utils.translation import gettext as _


def health(request):
    return {"message": _("Service is running.")}
```

Use `ngettext` for anything that varies with a count — Slovenian has
four plural forms, so `"%d items"` cannot be assembled by hand.

## After changing a string

```bash
uv run python manage.py update_translations
# translate the new entries in locale/sl/LC_MESSAGES/django.po
```

`update_translations` is `makemessages` with the project's options
(every language, no obsolete entries, file names without line numbers,
and staying out of `.venv`, `docs` and `tests`). It also keeps each
catalogue's `POT-Creation-Date` as it was: makemessages restamps it on
every run, and on a stack of branches that one line would conflict in
every one of them. A catalogue with nothing new is left untouched,
file time included.

Commit the `.po` files. The compiled `.mo` files are not committed;
they are gitignored and built from the `.po` files (see below).

A commit hook runs `update_translations`. If the catalogues lag the
source, it updates them and the commit stops, the way `ruff format`
does: translate the new entries, add the files, commit again. Because
it runs on every commit, each branch of a stack carries catalogues that
match its own source. CI runs the same hook, and
`test_the_projects_catalogues_match_the_source` runs
`update_translations --check` as a test.

## Incomplete translations

A language does not have to be complete to be committed, merged or
released. gettext already has the two states that matter:

| State in the `.po` | What the page shows |
|---|---|
| Translated | The translation |
| Untranslated (`msgstr ""`) | The English original |
| Unreviewed (`#, fuzzy`) | The English original, unless the language is in `TRANSLATIONS_SHOWING_UNREVIEWED` |

Mark a translation you are not sure of, a machine translation for
instance, with `#, fuzzy`; removing the flag is what reviewing it
means. Poedit and similar editors show the flag as "needs review".

`TRANSLATIONS_SHOWING_UNREVIEWED` in the settings lists the languages
whose unreviewed translations are shown anyway: for a language nobody
here can review, a machine translation beats English. It is empty.

`uv run python manage.py translation_status` counts, per language, the
strings still untranslated and those waiting for review. It never
fails. The commit hooks print it whenever strings or catalogues change,
and CI turns any gaps into warnings on the run and a table in its job
summary.

## Compiled catalogues

`src/hrcek/core/translations.py` builds the `.mo` beside each `.po`,
with polib rather than GNU gettext, so a server needs only the Python
dependencies. It runs:

- in the Docker image build (`manage.py compile_translations`), so a
  container starts with fresh catalogues and never writes to
  `/app/locale`;
- as the app starts (`CoreConfig.ready`), for every other install,
  including a development checkout and the test run;
- on demand: `uv run python manage.py compile_translations`.

A catalogue is built only when needed: when its `.mo` is missing, or
its modification time differs from the `.po`'s. A built `.mo` is
stamped with exactly its `.po`'s time, so any difference means rebuild,
not only a newer `.po`: a copy that keeps file times (`rsync -a`, a
tarball) can deliver a changed `.po` that looks older than the `.mo`
built from its predecessor. Each `.mo` is written under a temporary
name and moved into place, so workers starting together cannot see
half a file, and it takes its `.po`'s file mode: the image builds as
root and runs as another user.

Django loads the default language's catalogue while it imports models,
before any app's `ready()` runs. So when the startup build produces
anything, it clears Django's catalogue caches through the same hook the
development autoreloader uses for a changed `.mo`
(`django.utils.translation.reloader.translation_file_changed`);
otherwise a first start would keep the missing catalogue for the life
of the process.

If the app cannot write its locale directory at startup, it logs a
warning and carries on in English rather than refusing to start.

## How a language is chosen

`LocaleMiddleware` negotiates the language in order: the language
cookie first, then the request's `Accept-Language` header, against
`settings.LANGUAGES`. The cookie is set by Django's `set_language`
view, mounted at `/i18n/setlang/`; the footer's language switcher in
`base.html` posts to it. With no cookie set, the browser preference
decides — nothing is stored until somebody explicitly picks a
language. Error messages are resolved at render time, so a response is
in the caller's language rather than the server's.

In tests, force a language with `django.utils.translation.override`.
